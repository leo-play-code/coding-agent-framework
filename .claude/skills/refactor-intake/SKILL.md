# refactor-intake — 重構開案收料引導

重構卡住的地方幾乎不是「不會寫」,是**開案時材料不齊**:查詢條件對不上、欄位靠猜、輸出格式沒看過、
沒有舊系統的實際結果可以對。結果就是寫完再來回改,人工對資料對到死。

這個 skill 只做一件事:**在動任何程式碼之前,把材料清點乾淨,缺的當面要到。**
清完產出工單 manifest,交給下游做開發與驗收。

**一句話原則**:寧可現在多問三句,不要事後對三天。
**絕對禁止**用「(待確認)」「待補」帶過缺料就往下走 —— 那正是這個 skill 要根治的病。

## 何時用
- 要把一支或多支舊程式重寫成新系統,開案前。
- 一次要投遞 10+ 支程式做批量重構(每支一張工單)。
- 使用者說「我把東西丟給你了」但你不確定夠不夠。

## 上下游
```
refactor-intake(本 skill:收料 → 工單 manifest)
   ↓ docs/intake/manifest.json
開發(逐張工單實作)
   ↓
test-parity / acceptance-report(migration profile:逐格對等 + 驗收報告)
```
manifest **刻意採用 `acceptance-report` 的格式**(`meta` + `features[]`),收料狀態掛在各 feature 的
額外 `intake` 欄位下。下游 `gen-acceptance-report.mjs` 只讀已知欄位,額外欄位會被忽略,
所以**同一個檔從開案用到驗收,不需要任何轉換**。

## 五類材料(每張工單都要清點)

| 代號 | 類別 | 具體要什麼 | 缺了會怎樣 |
|---|---|---|---|
| `source` | 原始碼 | 舊程式檔本體 + 程式代碼(如 `aapr190a`) | 只能憑描述重寫,行為必然走樣 |
| `conditions` | 查詢類別/條件 | 每個查詢入口的參數、型別、預設值、必填與否 | 條件對不上 → 結果一定不同,且不會有人發現 |
| `fields` | 顯示內容與表格欄位 | 欄位名、型別、順序、小計/分組/總計列規則 | 逐格比對無從展開,驗收只能靠目視 |
| `outputSample` | 輸出樣本 | 匯出 Excel / 列印的實際檔或截圖 | 輸出格式驗不了(欄位順序、標題、合計位置) |
| `legacyFile` | 對照結果檔 **+ 其查詢參數** | 舊系統實際跑出來的匯出檔,**必須附產生它的參數** | 掉到證據力 C,只能證新系統自己跟自己一致 |

> `legacyFile` 有檔案但沒附參數 **等於沒有** —— 無法用相同條件重跑新系統,就無法逐格對。
> 這是最常見的缺料形態,務必單獨檢查。

每類判定三種狀態:`有` / `缺` / `不適用`。

## 材料放哪:使用者怎麼放都行,你負責認

**不要求使用者照任何規定結構擺檔案。** 實際情況是:使用者早就準備好一包東西丟在某個資料夾,
然後跟你說「我準備了這些」。要求他先整理成規定格式,等於把工作推回去,這個 skill 就沒意義了。

**你的工作是掃他的資料夾、自己認出哪個檔是哪一類材料。** 常見的實際樣貌:
- 一支程式一個子資料夾,裡面原始碼與匯出檔混在一起
- 原始碼一包、匯出的 Excel 另一包,靠檔名對應
- 全部平鋪在同一層,靠程式代碼(如 `aapr190a`)出現在檔名裡來歸屬

只有兩個硬要求,**其餘都由你判斷**:
1. 材料要放在**工作區檔案系統**,不要用對話附件 —— 附件不落地、重載會消失、有字元上限,
   而且之後 harness 要能直接讀到 legacy 檔。
2. 使用者要告訴你**資料夾在哪**(或你掃得到)。

**不要搬動或改名使用者的檔案。** manifest 記錄檔案**實際所在的路徑**即可。搬檔會讓使用者
找不到自己的東西,而且一旦認錯類別,搬完就更難回頭。

`docs/intake/manifest.json`(工單)與 `docs/intake/README.md` 是**你的產出**,放在專案的
`docs/intake/`;使用者的原始材料留在他原本放的地方。

**辨識線索**:
- 副檔名 `.xlsx/.csv` 且內容像報表結果 → 可能是 `legacyFile` 或 `outputSample`;
  **兩者的差別是「有沒有附產生它的查詢參數」**,分不出來就問使用者,別猜。
- 程式原始碼副檔名(`.4gl/.pas/.sql/.prg/.c` 等)→ `source`。
- 檔名或內容含程式代碼(如 `aapr190a`)→ 用來歸屬到哪張工單。
- CSV / Excel 可逐格解析,最有價值;PDF / 截圖只能人工目視,證據力較弱,要在工單標明。

## 產出流程

典型開場是使用者說「我把資料準備在 `<某資料夾>` 了,你看看還缺什麼」。以下四步都在同一輪對話內走完。

### Step 0 — 找到材料
使用者講了資料夾就用他講的;沒講就問(或先掃專案裡明顯的候選再列給他確認)。
**不要假設是 `docs/intake/`** —— 那是你的產出位置,不是他的投遞位置。

### Step 1 — 掃描辨識,並把「我認到什麼」攤給使用者看(核心)
遞迴列出資料夾內容,逐檔判斷屬於哪張工單、哪一類材料,**實際打開檔案確認**
(Excel 看得到欄位標題與資料列;原始碼看得出是哪支程式),不能只看檔名猜。

判定完**先把辨識結果整份列給使用者**,再往下走:

```
aapr190a 廠商應付帳齡
  ✅ 原始碼      aapr190a.4gl
  ✅ 對照結果檔  應付帳齡_0630.xlsx(12 欄 × 340 列)
  ❓ 查詢參數    未找到 —— 上面那個檔是用什麼條件跑的?
  ✅ 顯示欄位    從原始碼抽到 11 欄(廠商編號/廠商名稱/…/總計列)
  ⬜ 輸出樣本    未找到
```

**誤認比缺料更危險** —— 把「輸出樣本」當成「對照結果檔」,會讓後面拿錯檔去逐格對,
比對通過了也是假的。所以:
- 分不出來的**一律問**,不要猜。
- 沒有把握歸屬到哪張工單的檔案,列成「這些我不確定屬於誰」請使用者指認。
- 使用者說「有給」但你讀不到 → 以**你讀到的為準**,回報讀不到,別記成 `有`。

抽 `conditions` / `fields` 時忠實來自檔案內容;抽不出來就是 `缺`,不要推測補齊。

### Step 2 — 缺料主動索取(這個 skill 的重點)
把所有工單的缺料彙整,用 `AskUserQuestion` **一次問齊**,別一張一張來回。要點:

- **具體點名**:哪一張工單、缺哪一類、缺了會怎樣。
  ✅「`aapr190a` 的「應付帳齡_0630.xlsx」我找不到它是用什麼條件跑的(基準日?廠商?科目?)。
     沒有這組參數,我沒辦法用相同條件跑新系統來逐格對,這支就只能到證據力 B。」
  ❌「請提供更多資訊」
- **能在對話裡回答的就在對話裡收**。查詢參數、欄位小計規則這類,使用者直接講給你,
  **你寫進 manifest 即可,不要叫他去編輯 `params.md`** —— 要他填檔案就是把工作推回去。
  只有「檔案本身沒給」(缺原始碼、缺匯出檔)才需要請他補檔到資料夾。
- 使用者可以回「這項沒有 / 不需要」→ 記為 `不適用`,把該工單的 `evidenceTarget` 顯式降級,
  並寫進 `intake.waived[]`。**降級必須是使用者知情下的明示決定,不能是你默默放行。**

### Step 3 — 定驗收目標(evidenceTarget)
依材料齊備度定每張工單**開發完成後應達到的證據力**(分級定義與 `acceptance-report` 一致):

| 材料狀況 | evidenceTarget | 意義 |
|---|---|---|
| 有 legacy 檔 **且** 有對應參數 | **A** | 開發完要拿舊系統匯出檔逐列逐欄 diff 通過 |
| 無 legacy 檔,但邏輯可定恆等式 | **B** | 只能證內部一致(彙總==逐筆加總),未對本尊 |
| 兩者皆無 | **C** | 僅實作,無法驗證 —— 應盡量避免,先回 Step 2 要料 |

`verification.evidenceLevel` 一律先填 `"C"`(還沒開發,當然沒驗過);`evidenceTarget` 是目標。
**別把目標填進 evidenceLevel**,那是灌水。

### Step 4 — 產出工單 manifest
寫 `docs/intake/manifest.json`,格式見 `references/manifest.example.json`。
每筆 feature 除了 `acceptance-report` 的標準欄位,額外帶 `intake` 物件記錄收料狀態。

### Step 5 — 準備就緒關卡
- 任一工單有 `缺` 且未被使用者明示 `不適用` → 該工單 `intake.blocked = true` + 填 `blockedReason`。
- **回報一份就緒摘要**給使用者:幾張可開跑、幾張卡住、各卡在哪、目標證據力分佈。
- `blocked:true` 的工單**不得進入開發**,材料補齊前不要動它。

### Step 6 — 交棒給使用者
回報就緒摘要後**這一輪就結束**,由使用者決定接下來怎麼開發(在這個對話直接做、開新對話、或一輪
處理多支)。**不要自作主張接著實作整包工單** —— 一次要吃幾支是使用者的決定,不是你的。

> 曾經有「批量重構佇列」把每張工單各自開對話自動跑完,已於 2026-08-05 整個移除。所以:
> **不要寫 `docs/intake/.batch-go.json`、不要提「🏭 批量重構佇列」、不要讀 `CF_BATCH_REFACTOR`** ——
> 那些東西都不存在了,提了只會讓使用者去找一個沒有的面板。

## 常見坑
- **別要求使用者先整理成規定格式**:他準備好一包丟給你,認檔是你的工作。要他重排資料夾,
  這個 skill 就失去意義了。
- **「使用者說有給」不等於有**:一律實際讀檔判定。最常見的是匯出檔給了但沒說參數。
- **誤認比缺料更危險**:把輸出樣本當成對照結果檔,後面會拿錯檔逐格對,「通過」也是假的。
  分不出來就問。
- **不要用「(待確認)」往下走**:那會讓缺料在開發完才爆出來,正是要根治的問題。缺就問。
- **參數與匯出檔要一一對應**:一支程式可能有多個匯出檔(不同查詢條件),要逐檔記參數,
  不是整支記一組。
- **欄位清單要含順序與小計規則**:只有欄位名不夠,逐格比對會在總計列上失敗。
- **降級要留痕**:使用者說「這支沒有舊資料可對」→ 記 `不適用` + `evidenceTarget` 降 B/C + 寫進
  `waived[]`,讓驗收報告誠實反映「這支本來就沒對過本尊」。
- **不要搬動使用者的檔案**:manifest 記實際路徑就好。
