# edge-cases — 開 PR 前的風險交代

## 這個 skill 要解決什麼

CI 擋得住「語法錯、型別錯、build 不過、import 壞掉」。擋不住的是:輸入為空、條件組合沒定義、
連線斷掉。而這三類正好是 **AI 寫 code 時最容易漏的** —— 因為 AI 寫的是它腦中的典型案例,
而且它對自己寫的東西有信心,不會主動去懷疑。

審查的人也擋不住 —— 要他自己把這三件事逐一想過,等於要他補完你沒做的功課,結果就是 LGTM。

**所以這件事必須由寫 code 的人(你)在開 PR 前交代清楚,不是留給審查的人去發現。**

## 硬性規則

1. **沒處理就寫沒處理。** 這份交代的價值全在誠實。寫「已處理」但其實沒有,比不寫更糟 ——
   審查的人會因此跳過那一項。不確定就寫「不確定」。
2. **只寫這次改動涉及的。** 不要為了填滿格式去列無關的邊界。三項裡有哪項不適用,
   就寫「本次改動不涉及」,不要硬湊。
3. **每一項要指到具體位置**(`檔案:行號` 或函式名)。指不到位置的,表示你其實沒檢查。
4. **不要下「所以這樣是安全的」這種結論。** 只陳述你做了什麼、沒做什麼,判斷留給審查的人。

## 三類怎麼查

### a. 邊界值 —— 最容易壞的地方就在那

對每個有「量」的東西問一遍:

- 集合:**空的**會怎樣?**只有一筆**呢?**剛好等於上限**呢?超過呢?
- 數值:0、負數、最大值、剛好等於閾值(`>` 還是 `>=`?)
- 字串:空字串、只有空白、超長、含特殊字元
- 時間:月底、跨年、閏年、時區邊界(這個系統的 Gitea 是 UTC、宿主機是 UTC+8)
- 索引/分頁:第一頁、最後一頁、剛好整除、剩 0 筆

⚠️ off-by-one 幾乎都出在 `<` vs `<=`、`length` vs `length-1`。改動如果碰到迴圈或切片,
直接把邊界那兩筆列出來算一次,不要用看的。

### b. 判定表 —— 多條件組合有沒有漏

只要出現 2 個以上的布林條件,就把組合列成表格,逐格確認行為有沒有定義:

| 條件 A | 條件 B | 預期行為 | 程式碼有處理嗎 |
|---|---|---|---|
| 真 | 真 | … | ✅ `foo.ts:42` |
| 真 | 假 | … | ✅ `foo.ts:47` |
| 假 | 真 | … | ⚠️ **未定義** |
| 假 | 假 | … | ✅ 走 else |

N 個條件有 2^N 格。**不必每格都實作,但每格都要「知道會發生什麼」。**
最常漏的是「兩個都假」和「只有第二個成立」這兩格。

### c. 錯誤猜測 —— 不正常的時候會怎樣

逐一問:

- **空值**:上游給 null/undefined 會怎樣?是崩、是靜默略過、還是往下傳染?
- **外部依賴掛掉**:DB 斷線、API 回 500、檔案不存在 —— 錯誤會被看見嗎?
- **Timeout**:有設逾時嗎?**沒設就是無限等**。重試會不會打爆對方?
- **併發**:同時被呼叫兩次會怎樣?有共用狀態嗎?

⚠️ **AI 生成的程式碼在這裡有個固定壞習慣:讓錯誤消失。**
交代前先用 grep 掃過自己這次寫的 code:

```bash
# 這次改動裡所有可能吞掉錯誤的地方
git diff main...HEAD -U0 | grep -nE '^\+' | grep -E 'catch\s*\{\s*\}|\|\|\s*\[\]|\?\?\s*\[\]|except\s*:|except Exception:\s*pass|2>/dev/null'
```

每一個命中都要在交代裡說明**它吞掉的是什麼錯誤、為什麼可以吞**。
吞掉錯誤不一定錯,但「不知道自己吞了什麼」一定錯。

## 分流:能測的去測,要人決定的留給人

三類查完會得到一串「這裡沒處理」。**不要直接動手把它們全部補掉** —— 先分成兩堆:

**A. 可自動驗證的缺陷** → 進下面的修復迴圈
判準:能寫成一個「給定輸入 X,預期行為 Y」的測試,而且 Y 是客觀的(不需要問任何人)。
例:空陣列進來會拋 `TypeError`、off-by-one 少算最後一筆、null 往下傳染造成崩潰。

**B. 需要人決策的** → 不要碰,寫進交代區塊給審查者
判準:要決定「該怎麼辦」而不是「修好它」。
例:超過 1000 筆要不要分頁、「A 假 B 真」那格該回 403 還是空清單、逾時該設幾秒、
重試幾次。**這些你猜不出來,猜了就是替使用者做決定。**

⚠️ **最危險的失敗模式:為了讓警告消失而加防禦性程式碼。**
把 B 類硬修成「不報錯」,最常見的手法就是補一個 `if (!x) return []` / `catch {}` —— 那
正好製造出這個 skill 要抓的無聲失敗,而且從此再也沒人會發現。**寧可留一個誠實的 ⚠️,
也不要一個讓檢查變綠的假修復。**

## 修復迴圈(只跑 A 類)

對每個 A 類缺陷:

1. **先寫測試,而且先確認它是紅的。** 沒看過它失敗,就不知道測的是不是真的那件事 ——
   一個永遠綠的測試比沒有測試更糟。
2. 修 code。
3. **重跑整個測試檔**(不只新加的那個)—— 確認沒有修 A 弄壞 B。
4. 還是紅的 → 回到步驟 2。

**上限三輪。** 三輪修不好就停,把它從 A 類移到交代區塊,寫清楚「試過什麼、為什麼沒修好」。
無限重試只會讓 AI 越改越大、把一個小缺陷擴散成一次重構。

測試放哪、用什麼框架:照專案既有慣例(先找現有測試檔來看)。專案完全沒有測試基礎建設時,
不要為了這個 skill 從零建一套 —— 改成把 A 類也寫進交代區塊,並在交代裡註明「無測試基礎
建設,未驗證」。

跑完之後,**測試結果要真的貼出來**(通過幾個、失敗幾個)。說「都過了」但沒有輸出,等於沒跑。

## 輸出:貼進 PR 描述的區塊

跑完後產出這段,放進 PR 描述(接在做法說明之後):

```markdown
## 風險交代

**已修復並補上測試**(A 類,已跑到綠燈)
- 輸入為空陣列會拋 TypeError → 修 `service.ts:88`,測試 `service.test.ts:34` ✅
- 分頁最後一頁少算一筆(off-by-one)→ 修 `page.ts:42`,測試 `page.test.ts:19` ✅
- 測試結果:`12 passed, 0 failed`(`npm test -- service page`)

**需要你決定**(B 類,我沒有動)
- 超過 1000 筆會一次全載入記憶體(`service.ts:70`)—— 要不要分頁?上限多少?⚠️
- `isAdmin` × `isOwner` 的「非 admin 且非 owner」那格目前走 else 回 403(`guard.ts:21`),
  這是我沿用既有慣例猜的,不確定是不是你要的 ⚠️
- 外部 API 未設 timeout,會無限等(`client.ts:15`)—— 該設幾秒?重試幾次?⚠️

**試過但沒修好**(三輪上限)
- (本次無)

**其他**
- 本次沒有新增 catch 空區塊(已用 grep 確認)
```

沒有 ⚠️ 的時候也要留著這個區塊 —— 一份經常出現「未處理」的交代,才會讓沒有 ⚠️ 的那次
真的被相信。全部都寫「已處理」的交代等於沒寫。

## 三項的份量

- **debug / 改一行 / 純格式**:三項各一句帶過即可,不必展開判定表
- **加 feature / 改邏輯**:完整跑三項
- **動到權限、金額、資料刪除、schema、對外 API**:判定表一定要列出來,異常路徑一定要逐項寫
