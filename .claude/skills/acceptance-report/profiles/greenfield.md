# profile: greenfield — 全新功能(對 spec 驗收準則)

適用:沒有舊系統可對,功能來自需求/spec。基準 = **需求的驗收準則**。

## 驗收準則來源(acceptance[])
從需求文件抽出**可操作、可判 PASS/FAIL 的具體行為**,一條一驗:
- 來源優先序:`SPEC.md` / PRD / issue 的驗收準則 → 若沒有,先跑 `spec` skill 把模糊需求變成 executable spec,再抽。
- 每條寫成 User 能實際做的動作 + 預期結果。含**正常路徑 + 邊界 + 錯誤情況**。
  - 例:「輸入已存在的 email 邀請 → 顯示錯誤,不重複建立」。
- 抽完把準則的來源記進 `verification.criteriaSource`(如 `SPEC.md#邀請流程`),方便回溯。

## 驗證基準與策略(verification)
- `baseline`:spec 的驗收準則(標清哪份哪節)。
- `strategy`:`verify` skill 端到端把每條準則跑一遍 + 單元/整合測試涵蓋準則。
- 提升證據力:
  - **A** — `verify` 把每條驗收準則實際跑過通過,且測試涵蓋。
  - **B** — 有單元測試綠,但未端到端跑驗收準則。
  - **C** — 僅實作完成。

## 常見坑
- 驗收準則不要照抄需求標題(抽象);要拆成能勾的具體行為。
- 邊界/錯誤情況最容易漏 → 每個功能至少一條負向準則。
